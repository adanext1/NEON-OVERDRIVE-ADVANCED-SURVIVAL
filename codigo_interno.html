Estado Actual de la Base de Código

El simulador de combate de NEON OVERDRIVE ha crecido de manera orgánica incorporando cooperativo local offline, multijugador online mediante WebSockets, interfaces móviles y múltiples clases de enemigos. Como consecuencia, varios archivos lógicos del directorio /js han aumentado considerablemente su volumen, dificultando las tareas de mantenimiento y depuración del simulador.

js/game.js 117 KB (2,698 líneas)

Impacto: Archivo principal sobrecargado. Agrupa la renderización completa de elementos en pantalla, el cálculo del bucle físico y las rutinas de fin de oleada.

js/ui.js 72 KB (1,530 líneas)

Impacto: Mezcla manipulación básica de elementos del DOM con la lógica del chasis y la compleja navegación de cursor por gamepad del Nexus de Ensamblaje.

js/data.js 37 KB (476 líneas)

Impacto: Almacena todas las variables de estado y catálogos globales. Representa la raíz de datos común leída y modificada por todos los demás scripts.

Análisis de Acoplamiento: Los scripts del simulador utilizan un espacio de nombres global compartido. Aunque esta arquitectura simplifica la sincronización de elementos rápidos en un juego web con renderizado dinámico en Canvas, genera una fuerte dependencia entre la representación gráfica y las reglas físicas de juego.

Estrategia de Modularización Sin Rupturas

Para mantener la compatibilidad con ejecuciones locales directas (usando el protocolo file:/// sin necesidad de levantar servidores locales) y evitar incompatibilidades de CORS, se desaconseja migrar a Módulos nativos de JavaScript (type="module" / import-export).

En su lugar, la estrategia óptima consiste en **desacoplar las funciones de forma lógica en archivos javascript independientes, manteniendo el espacio de nombres global unificado en data.js**. Esto permite reducir a menos de la mitad el tamaño de los monolitos principales manteniendo intacta la lógica de red, co-op offline y controles.

Importante (Orden de Carga en p.html): La separación lógica obliga a un orden de carga riguroso en el código HTML de importación de scripts, asegurando que los datos base se carguen antes de inicializar los sistemas gráficos y de entrada.

Estrategia para la Implementación de Multilenguaje (i18n)

Para traducir el juego de forma eficiente se plantean tres rutas de implementación técnica, diferenciando la traducción manual controlada de la traducción automática en tiempo real:

Comparativa: Traducción Manual vs. Automática en tiempo real

Método Funcionamiento Técnico Ventajas Desventajas / Riesgos
1. Traducción Manual (Diccionario Local)
[RECOMENDADO]		 Los textos se redactan manualmente en js/locales.js de forma estructurada. Control total del vocabulario del videojuego (ej: traducir "dash" como "desplazamiento rápido" y no como literal "guion"). Funciona 100% offline. Requiere redactar manualmente cada texto nuevo que se introduzca en el juego.
2. Traducción Automática (API deepL / Google) El juego envía las cadenas a un endpoint de traducción externo por HTTP en tiempo de ejecución. Soporta traducción al vuelo de comentarios de usuarios o mensajes de chat de salas dinámicas en red. Requiere internet obligatorio, expone claves API del lado del cliente y las traducciones literales dañan la jerga gaming.
3. Traducción Semiautomática (Híbrida) Un script en Node.js traduce automáticamente el archivo base (ES) a inglés usando la API de OpenAI/DeepL al empaquetar, generando el archivo local. Combina la rapidez del traductor automático con la posibilidad de corregir errores manualmente antes de publicar. Requiere configurar un paso extra (build step) en el pipeline de desarrollo.
Decisión de Diseño: Se aconseja combinar la **Traducción Manual (Opción 1)** para todas las interfaces, menús del chasis y HUD, y usar **Traducción Automática (Opción 2)** únicamente para traducir mensajes del chat multijugador online si se desea soportar salas internacionales.

// js/data.js o js/locales.js
let currentLanguage = localStorage.getItem('neon_overdrive_lang') || 'es';

function _t(path, replacements = {}) {
    const keys = path.split('.');
    let translation = LOCALES[currentLanguage];
    
    for (const k of keys) {
        if (translation && translation[k] !== undefined) {
            translation = translation[k];
        } else {
            return path; // Fallback
        }
    }

    Object.keys(replacements).forEach(key => {
        translation = translation.replace(`{${key}}`, replacements[key]);
    });

    return translation;
}

// js/locales.js o js/data.js - Carga dinámica del JSON de traducción manual

function loadCustomLanguageFile(event) {
    const file = event.target.files[0];
    if (!file) return;

    const reader = new FileReader();
    reader.onload = function(e) {
        try {
            const json = JSON.parse(e.target.result);
            
            // Validar que contenga la estructura requerida del diccionario
            if (json.menu && json.game && json.nexus) {
                // Inyectar el idioma personalizado en LOCALES
                LOCALES['custom'] = json;
                currentLanguage = 'custom';
                
                // Persistir la elección y el contenido
                localStorage.setItem('neon_overdrive_lang', 'custom');
                localStorage.setItem('neon_overdrive_custom_json', JSON.stringify(json));
                
                // Actualizar los textos de la interfaz en tiempo real
                if (typeof updateUINames === 'function') updateUINames();
                
                showNetworkMessage("¡Archivo de traducción manual aplicado correctamente!");
            } else {
                alert("Error: El JSON no cuenta con las secciones requeridas ('menu', 'game', 'nexus').");
            }
        } catch (err) {
            alert("El archivo cargado no es un JSON válido.");
        }
    };
    reader.readAsText(file);
}

// Cargar idioma personalizado en el arranque del juego

Sincronización en la Nube y Soporte para Reporte de Errores

Para ofrecer una experiencia de juego moderna y simplificar la resolución de problemas (bugs), se detalla la arquitectura técnica para sincronizar partidas y un sistema de reporte de errores integrado con captura de datos lógicos y subida de archivos multimedia manual por parte del usuario.

1. Sistema de Guardado en la Nube (Cloud Save)

El avance se guarda localmente en localStorage. Para sincronizarlo en la nube de forma eficiente, se propone un modelo de resolución de conflictos basado en marcas de tiempo (timestamps).

  • Flujo de Autenticación: Formulario de login ligero integrado en el menú. Tras el inicio de sesión, el servidor devuelve un token JWT y los datos de guardado vinculados al perfil del usuario.
  • Resolución de Conflictos: Cada vez que se realiza un guardado, se añade el campo lastSyncTimestamp: Date.now(). Al iniciar la sesión en un nuevo dispositivo, se comparan las marcas de tiempo local y en la nube, mostrando un modal de decisión si hay discrepancias.

2. Autenticación Simple (Nombre de Usuario y PIN)

Para implementar una autenticación sumamente ligera e intuitiva para los usuarios (sin necesidad de complejos flujos de email o confirmaciones de contraseñas), se propone un sistema basado en **Nombre de Usuario único y un PIN numérico de 4 dígitos**.

Flujo de Autenticación Simple: El usuario escribe su nombre y un PIN de 4 números. Si el usuario no existe, el sistema lo registra automáticamente en la base de datos vinculando ese PIN. Si existe, valida que el PIN coincida y descarga su perfil.

// js/network.js - Implementación de Login Simple

async function executeSimpleLogin() {
    const username = document.getElementById('login-username').value.trim();
    const pin = document.getElementById('login-pin').value;

    if (!username || pin.length !== 4 || isNaN(pin)) {
        showNetworkMessage("Escribe un usuario y PIN de 4 números válidos");
        return;
    }

    try {
        let response = await fetch('/api/auth/simple', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ username: username, pin: pin })
        });

        let resData = await response.json();
        
        if (response.ok) {
            // Guardar datos de sesión localmente
            userSave.cloudProfile = {
                username: username,
                authToken: resData.token,
                isSynced: true,
                lastSyncTimestamp: resData.saveData ? resData.saveData.lastSyncTimestamp : 0
            };
            
            // Si el servidor tenía una partida guardada más nueva, sobreescribir la local
            if (resData.saveData && resData.saveData.lastSyncTimestamp > (userSave.lastSyncTimestamp || 0)) {
                userSave = Object.assign(userSave, resData.saveData);
            }
            
            saveGame();
            showNetworkMessage("¡Sesión iniciada y sincronizada!");
            document.getElementById('login-modal').style.display = 'none';
        } else {
            showNetworkMessage("Error: " + resData.message);
        }
    } catch (err) {
        showNetworkMessage("Fallo de conexión con el servidor de nube");
    }
}

3. Buzón de Feedback y Reporte de Bugs (Subida Manual de Archivos)

Para respetar la privacidad de los usuarios, reducir el consumo de CPU y evitar sobrecargar el ancho de banda con capturas automatizadas, se descarta la grabación de pantalla del canvas en segundo plano.

En su lugar, se propone un **sistema de reporte manual** donde el usuario escribe sus comentarios y, opcionalmente, **adjunta una imagen (captura de pantalla) o un vídeo corto (en caso de que estuviera grabando por su cuenta)** usando campos estándar de selección de archivos.

Ventajas del Reporte Manual: 1. **Privacidad:** El juego no captura vídeo ni audio sin consentimiento expreso. 2. **Compatibilidad:** Evita el overhead de la API de grabación (MediaRecorder) en dispositivos móviles de gama baja. 3. **Filtro de Ruido:** Los reportes se envían solo cuando el usuario decide conscientemente documentar un bug real.

// js/diagnostics.js - Emisor de reportes de errores manuales

async function submitManualBugReport() {
    const comments = document.getElementById('bug-comments').value.trim();
    const imageInput = document.getElementById('bug-image-file');
    const videoInput = document.getElementById('bug-video-file');

    if (!comments) {
        showNetworkMessage("Por favor, añade una descripción del error");
        return;
    }

    // 1. Recopilar telemetría de depuración del estado del juego automáticamente
    const systemState = {
        wave: wave,
        enemiesCount: enemies.length,
        activePlayers: players.length,
        isCoop: isCoop,
        isOnline: isOnline,
        userAgent: navigator.userAgent,
        recentConsoleErrors: window.recentConsoleErrors || []
    };

    // 2. Empaquetar todo en Multipart Form Data
    const formData = new FormData();
    formData.append('comments', comments);
    formData.append('systemState', JSON.stringify(systemState));

    if (imageInput.files && imageInput.files[0]) {
        formData.append('screenshot', imageInput.files[0]);
    }
    if (videoInput.files && videoInput.files[0]) {
        formData.append('video', videoInput.files[0]);
    }

    try {
        let response = await fetch('/api/bugs/report', {
            method: 'POST',
            body: formData // Multipart/form-data automático
        });

        if (response.ok) {
            showNetworkMessage("¡Gracias! Reporte de bug enviado correctamente.");
            // Limpiar campos del formulario...

            showNetworkMessage("Error al procesar el reporte en el servidor");
        }

2. Integración Técnica de SDKs de Anuncios (Ad Networks)

Para evitar fallos lógicos si el juego se ejecuta offline o en un portal que no carga los scripts de Poki o CrazyGames, se debe diseñar una capa de abstracción segura. Un módulo centralizado (js/monetization.js) se encargará de realizar las llamadas condicionales. 

// js/monetization.js - Adaptador seguro para Ads

const AdManager = {
    sdkLoaded: false,
    platform: "crazygames", // "poki", "crazygames", o "none"

    init() {
        // Comprobar si el SDK de la plataforma está cargado en window
        if (window.CrazyGames && window.CrazyGames.SDK) {
            this.sdkLoaded = true;
            this.platform = "crazygames";
        } else if (window.PokiSDK) {
            this.sdkLoaded = true;
            this.platform = "poki";
        } else {
            this.platform = "none";
        }
    },

    showRewardedAd(onSuccess, onFailure) {
        if (!this.sdkLoaded) {
            // Si no hay internet o red de anuncios, simular éxito o fallo localmente
            onSuccess();
            return;
        }

        if (this.platform === "crazygames") {
            crazygamesSDK.ad.requestAd('rewarded', {
                adStarted: () => { togglePauseGame(true); },
                adFinished: () => { togglePauseGame(false); onSuccess(); },
                adError: () => { togglePauseGame(false); onFailure(); }
            });
        } else if (this.platform === "poki") {
            PokiSDK.rewardedAdOpportunity().then(success => {
                if (success) { onSuccess(); } else { onFailure(); }
            });
        }
    }
};

3. Mecánicas de Monetización en el Gameplay

  • Anuncios Recompensados (Rewarded Ads): Ofrecidos de manera opcional en las transiciones lógicas del simulador. Por ejemplo, en la pantalla de Game Over se puede ver un anuncio a cambio de **doblar los créditos obtenidos en la oleada** o conservar los materiales recolectados tras colapsar.
  • Anuncios Intersticiales (Interstitials): Vídeos cortos obligatorios (de 5 a 15 segundos) colocados estratégicamente al pulsar "INICIAR SIMULACIÓN" o "REINICIAR SIMULACIÓN". Nunca deben irrumpir en mitad de una oleada para mantener una buena experiencia de usuario.
  • Compras de Cosméticos (Microtransacciones): Si se integra una base de datos de usuarios (stubs de nube en data.js), se pueden desbloquear diseños especiales y skins para las naves (ej. estelas de motor personalizadas, colores neón únicos) usando pasarelas como Stripe o PayPal.

4. Seguridad en Guardado Local (Prevención de Hacks)

Dado que los progresos y créditos de los jugadores se almacenan de forma local en localStorage, es muy fácil para los usuarios alterar su saldo de créditos directamente desde la consola del navegador.

Solución Técnica (Save Signing): Para evitar trampas que rompan la economía del juego, se puede encriptar o firmar el JSON del save con un hash SHA-256 utilizando una clave secreta. Al cargar el save en data.js, el juego calcula de nuevo el hash de los datos cargados y, si no coincide con la firma guardada, se detecta manipulación y se limpia o advierte el perfil.

Técnicas de Optimización y Rendimiento

La reorganización física del código en módulos especializados facilita la implementación de mejoras avanzadas de rendimiento dirigidas a la GPU y la gestión del Garbage Collector de los navegadores.

1. Object Pooling (Reciclaje de Elementos en Memoria)

Problema Actual: Cada disparo y explosión añade dinámicamente objetos al heap mediante bullets.push() o particles.push(). Al desaparecer, el recolector de basura del navegador (Garbage Collector) interrumpe la simulación para liberar memoria, causando micro-tirones (stuttering).

Solución Recomendada: Definir colecciones con un número máximo de elementos inactivos al iniciar. En lugar de instanciar nuevos objetos lógicos, se activan y reposicionan elementos ya cargados en memoria, reduciendo la carga del recolector de basura a cero durante la partida.

2. Caching de Gráficos (Offscreen Canvas)

Problema Actual: La cuadrícula del fondo y los efectos geométricos estáticos se dibujan línea por línea 60 veces por segundo, consumiendo recursos de procesador del Canvas 2D.

Solución Recomendada: Renderizar la cuadrícula una única vez en un elemento Canvas oculto en memoria al cargar el simulador. Durante el frame rate normal, el buffer se copia instantáneamente en el canvas de dibujo principal utilizando ctx.drawImage(offscreenCanvas, 0, 0), liberando la carga del hilo principal.

3. Optimización de Eventos (Event Delegation)

Problema Actual: Las interfaces de compra y el inventario multi-panel añaden event listeners individuales por cada celda de componente, lo que consume memoria del DOM.

Solución Recomendada: Capturar los clicks en el contenedor superior (Nexus container) y determinar qué celda fue presionada a través del atributo event.target.dataset.id, simplificando la pila de listeners activos.
